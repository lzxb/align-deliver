# 对齐交付

所有给用户看的话，都按 [references/explain-clearly.md](references/explain-clearly.md) 写：一句话结论 + 最小示例 + 能画就画，全程中文；删掉不影响用户判断的话，一次只问一个问题。

## 四个阶段

适用于任何工作，不只是研发。只有提交到 git 的内容走 MR；其他交付物不按批次停下等验收，全部工作做完后一次交给用户，用户验收通过才结束。

## 分工：谁定什么

| 谁 | 定什么 |
|---|---|
| 用户 | 目标、任务原则、新原则、开工 |
| AI | 原则之内的所有细节，并写明“依据原则 N” |

**确认**：只有用户明确说“确认”或“开始”才算。用户回答了问题、说“可以”“好的”、没有回复、AI 自己推荐了方案，都不算确认。初始目标与原则必须先确认；开工后出现新原则问题，按 Q–R 先推进不受影响的工作，受影响部分在确认前暂停。

## 状态文件

E（讨论清楚？）通过后，把目标、核心原则、任务原则、批次表写入状态文件；之后每批开始前、每轮验收前都先重读它：

```
台账在 git 目录内：$(git rev-parse --git-common-dir)/align-deliver/<任务标识>.md
台账在工作目录内：.align-deliver/<任务标识>.md，不随交付物交出
```

非 git 交付物的工作副本放在台账同一目录下的 `<任务标识>/` 子目录，与台账一起避开工作树。这条只决定台账与工作副本的存放位置，不改变交付路径：任务含任一 git 交付，或工作目录位于 git 仓库内时，台账放在 git 目录内，避免被误提交；其余情况放在工作目录的 `.align-deliver/`。一个任务只用一个台账。

git 任务的台账放在 git 目录内，不会被提交；两类台账在上下文压缩后都不会丢。该文件是整个目标的台账，后续批次、定时运行都复用同一个任务标识与入口；不能只记录当前 MR。保存所有批次、源分支、MR 标识与远端状态、非 git 交付物及验收状态、待恢复操作、定时任务标识及执行互斥信息，字段与恢复方式见 [references/phase-4-maintain.md](references/phase-4-maintain.md)。

每轮验收记录、新增原则和交付说明也写入台账。待定原则须记录影响范围、依赖、已完成独立工作及验证；每个远程写入前先保存意图，调用后保存已确认结果或“结果未知”。不得把凭据、令牌写入台账。
