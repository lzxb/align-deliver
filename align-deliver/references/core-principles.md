# 核心原则

每个对齐交付任务都适用。对齐阶段按编号逐条复述，MR 描述中按编号完整列出，专家团按编号逐条验收。提交后的维护仍遵守这些原则：有工作先做，远程失败保留恢复路径，直到本任务全部 MR 已合并、关闭或取消。

1. **围绕目标讨论原则，按原则决策，不打补丁**：需求和讨论都只围绕目标讨论原则，不讨论细节。用户定目标、原则和开工，初始对齐必须先确认；AI 定原则之内的细节，并写明依据哪条原则。开工后遇到原则缺失或冲突，只暂停依赖该原则的部分，先完成并验证独立工作，再讨论仍然阻塞任务的问题；没有可独立推进的工作时立即提问。不得假定待定原则的答案或把未决项算作完成；讨论只问原则、附最小示例，不让用户选实现方案，也不打补丁。
2. **不主动扩大需求范围**：范围由目标和原则决定，原则要求覆盖的都在范围内，不能预设例外；超出目标的发现只记为“范围外建议”，不实施。
3. **不越层修改**：业务层的问题不改框架；框架改动必须先讨论，经用户批准。
4. **一个 MR 只做一件事**：顺手发现的问题单独记录，不混入当前 MR。
5. **极简优先**：先给最小的 API、最小的示例；感觉复杂就回退重新设计。
6. **以最新上游为准，独立 worktree**：每个任务在独立 worktree 中工作，从同步后的最新上游拉分支；方案和代码都基于最新代码。
7. **结论标注证据等级**：实测 / 读代码 / 推断。
8. **讲清楚**：先给一句话结论，再给最小示例；适合比较或说明关系时使用图表，必要的新概念先解释，全程中文，删去不影响判断的信息，一次只问一个问题。MR 正文须能独立理解，不复制本机路径或技能内部相对链接。
