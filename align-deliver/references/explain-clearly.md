# 讲清楚

对齐交付全程，所有给用户看的话（复述理解、汇报、提问、MR 描述）都按这份规则写。

## 回答的形状

```
一句话结论 → 最小示例（改动前 → 改动后）→ 图 / 表 → 需要用户决定的事（有才写）
```

**该不该写**：每一句都问一遍——删掉这句，用户还能不能做出判断？能，就删。过程、背景、用户已经知道的事、重复的话，都删。

| 句子（用户问“MR 能合并吗？”） | 删掉后还能判断吗 | 留不留 |
|---|---|---|
| “我先同步了上游，又跑了一遍测试……” | 能 | 删 |
| “能合并：CI 绿，无冲突。” | 不能 | 留 |
| “待你决定：影响还没统计，要等统计完再合并吗？” | 不能 | 留 |

## 规则

| # | 规则 | 反例 | 正例 |
|---|---|---|---|
| 1 | 一句话直接回答 | “先介绍一下背景：这个模块最早是……” | “不通过：删除了 3 个对外接口，违反原则 3。” |
| 2 | 必须给最小示例 | “参数的处理方式在多个地方不一致……” | `getUser(id)` → `getUser({ id })` |
| 3 | 能画就画 | 用三段文字描述两个模块的依赖关系 | 一张表：谁调用谁、传什么、返回什么 |
| 4 | 新词先解释，否则不用 | “这里触发了 stale closure” | “回调里拿到的是旧值，因为它在第一次渲染时就固定了” |
| 5 | 不打比方，说真实问题 | “把缓存想成一个仓库管理员……” | “缓存的 key 没有包含用户 ID，所以 A 看到了 B 的数据” |
| 6 | 不写过程 | “我先试了方案 A，测试失败，又去看日志才发现……” | “原因：时区没有转换。已修复。” |
| 7 | 能做的先做 | “要不要我去查一下？” | “查了：这个 MR 已经包含该提交，可以关闭。” |
| 8 | 全程中文 | 整段英文汇报 | 中文汇报，代码和命令保持原样 |
| 9 | 一次只问一个问题 | “请确认：1. … 2. … 3. …” | “待确认：原则 3 是否成立？” |
