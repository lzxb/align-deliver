# MR 描述模板

提交、更新或补交 MR 都用这四节。正文帮助读者审查本次交付，不复制技能全文或执行手册。

````markdown
## 目标

<一句话说明要解决的问题和完成结果>

## 原则

核心原则：

1. 按目标和原则决策，待定时先完成独立工作。
2. 不主动扩大需求范围。
3. 不越层修改，框架改动先经批准。
4. 一个 MR 只做一件事。
5. 极简优先。
6. 基于最新上游，在独立 worktree 工作。
7. 结论标注实测、读代码或推断。
8. 表达简洁，MR 能独立理解，引用可访问。
9. 只提交交付所需内容，任务执行经过和临时产物留在任务工作区。

任务原则（有才写）：<仅列已确认的本任务专属约束，每条一句话>

## 改动

- <本 MR 的主要改动及行为结果>
- <重要选择才补充理由及依据的核心/任务原则编号>

## 验证

| 检查 | 结果 | 证据 |
|---|---|---|
| 专家验收 | <最终一轮结论与文件修改数；通过须为 0> | <实测 / 读代码 / 推断> |
| 适用检查 | <实际检查范围与结果> | <实测 / 读代码 / 推断> |
| CI 与合并性 | <当前提交、流水线状态、与最新上游是否冲突> | <已核实的链接或结果> |

<有助于判断的风险、未覆盖范围或待处理事项；无则不写>
````

## 填写要求

- 核心原则保留全部编号，每条只写一句摘要；完整规则仍按技能执行。任务原则只写本任务专属约束，不重复核心原则或抄录讨论历史。正文自包含是让读者理解改动，不是搬入规则全文。
- 改动只描述本 MR 的有效交付。重要选择简写理由与原则依据；确有取舍才说明，确有助于理解才给最小示例、前后对比或图表，不为每个实现细节套固定栏目。
- 多批次时说明本 MR 的边界及必要依赖；前序 MR 已终态时如实写明。风险、截图、范围外建议或维护状态仅在有助于审查时补充；维护只写当前事实或阻塞，不重复操作流程，不留空栏目。
- 验证按实际范围和证据填写；最终完整专家验收须为 0 修改，CI 必须对应当前源提交。排队、运行中、失败或未知不能写通过；必要时注明上游故障及证据。逐轮过程和完整日志留台账。
- 按核心原则 9 核对实际差异和产品文档，任务执行过程及临时产物不入库；按已确认目标和实际持续用途判断，不能靠改名或未来可能复用放行。MR 不复制本机路径或技能内部相对链接；必要引用须核对网页内容、访问性与锚点，无法核实则内联必要说明。

模板精简只改变 MR 的表达；提交、失败恢复和覆盖全部 MR 的持续维护仍按技能流程执行。
