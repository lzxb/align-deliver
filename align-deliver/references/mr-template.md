# MR 描述模板

提交 MR 和补交待交付 MR 都用这一份。各节顺序固定；“批次”只在批次 > 1 时填写，“截图”和“范围外建议”有才写。

````markdown
## 目标

<一句话目标；用户用 /goal 设定过的，写原文>

完成标准：<可验证的标准>

## 核心原则

- <本次代码设计所依据的原则编号和约束；不照抄 Agent 通用工作规则>

## 任务原则

- <本次需求的实质约束，例如兼容性、职责或权限边界>

## 批次

| 批次 | 一句话 | 边界 | 状态 |
|---|---|---|---|
| 1 | <做什么> | <含什么，不含什么> | 已合并 |
| **2** | **<做什么>** | **<含什么，不含什么>** | **本 MR** |
| 3 | <做什么> | <含什么，不含什么> | 待做 |

依赖：<本批依赖的上一批 MR，如 !123；不依赖则写“无”>

## 决策说明

### 决策 1：<决策>

- 依据：原则 <N>
- 理由：<为什么>
- 放弃的方案：<方案，以及放弃的原因>

改动前：

```ts
// <同一个输入，改动前得到的结果>
```

改动后：

```ts
// <同一个输入，改动后得到的结果>
```

## 验收证据

| 轮次/检查 | 结论 | 修改文件 | 证据 |
|---|---|---|---|
| 第 1 轮 | <如：发现 3 处违反任务原则 2> | 4 | 读代码 |
| 第 2 轮 | <如：修复后复查 1 处> | 1 | 实测 |
| **第 3 轮** | **无问题** | **0** | **实测** |
| lint / 类型检查 / 测试 | <结果> | — | 实测 |
| CI | <通过 / 待运行 / 运行中 / 失败 / 查询未知；上游问题附证据，不冒充通过> | — | 实测 |

截图（可选）：

- 第 2 轮 · 模拟器：<图片>

## 范围外建议

- <专家团发现、但超出本次目标的问题，未实施>
````

## 填写要求

- 只写影响本次代码设计、公开行为和验证结果的内容；调度、重试、分支操作、台账、本机同步等执行安排留状态文件，不得换成“任务原则”抄入 MR。完整执行原则照常遵守。
- 路径用于定位文件，不替代必要说明。技能中对其他文档的要求，生成 MR 时写成正文中的具体规则；只把路径改成代码样式仍不足以让读者理解。
- 确需引用文件时，使用仓库中已核对的网页链接，优先固定到提交。提交、更新或补交 MR 前，核对实际目标文件、访问权限与锚点；无法验证的引用不用作依据，改为内联必要内容，不猜测或编造 URL。
- 一个决策对应一组“改动前 → 改动后”，多个决策分开列。前后两段用同一个输入，展示决策带来的结果变化，不是只贴改动后的代码写法。
- 最小示例只保留决策影响的几行；一眼看不出差别，说明决策还没讲清楚。
- 批次表从对齐阶段的表原样复制，只更新状态列，本 MR 所在行加粗。
- 验收证据表的最后一轮必须是 0 修改；每一轮的结论都写明发现的问题违反了哪条原则（如“违反任务原则 2”），说不出违反哪条原则的修改，就不该改。
- 每个决策写明原则依据；保留取舍和同一输入的前后结果，不复制讨论历史。
- CI 失败不是本 MR 引起的，不扩大范围修复；在 CI 行附证据，保持阻塞/待恢复，不记为绿灯。待运行或未知也不能填“实测通过”。
- 汇报分别使用已提交待处理、待恢复、已合并、已关闭、已取消；不把关闭/取消或一轮检查结束写成目标成功。
